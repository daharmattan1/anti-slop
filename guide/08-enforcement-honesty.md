# A gate is a tripwire, not a wall

The most dangerous thing you can believe about a quality gate is that it makes the bad outcome impossible. A gate you trust to be airtight is a gate you stop watching, and once you stop watching, the thing it was built to stop can walk around it while you assume it can't. Most gates are tripwires. They catch the honest mistake and the lazy shortcut, they make a deliberate bypass louder, and they do not make that bypass impossible. Calling a tripwire a wall does not make it one, it just means that when something steps over it, you find out later than you should have.

So the first job is to be honest about what a given control actually does. Take a rule that sounds absolute, that everything which gets published has to pass through the checker. In practice the checker watches one path, the normal way files get written, and it inspects anything that comes through there.

A file does not have to come through the normal path, and that is the hole. Copy a raw draft straight onto the published folder with a plain shell command, and the checker never sees it, because the command it was watching for was not the one you used. The draft lands unchecked, next to the pages that did pass. When this was actually tested, the file appeared on the live path and the checker's log recorded nothing at all, because the write it was built to inspect never happened.

That is the difference between a tripwire and a wall, and it is worth holding onto. A wall makes a path impossible. A tripwire notices when someone takes the path it is watching, and stays blind to the paths it is not. Almost every gate you will build is the second thing. This is not a reason to throw it out. The tripwire still catches the ordinary failures, the ones that are careless rather than adversarial, and those are most of them. It is a reason to stop describing it as the first thing, because the description is what makes you careless.

What actually raises the bar higher than a tripwire is a boundary in who is allowed to do what. Call it a promotion boundary. The worker that writes the draft is not handed the tools that would let it place a file on the final path. It has no shell and no copy command, so it cannot move a finished file onto the live path the way that bypass did; it writes into a scratch area and stops. A separate step, one with more trust and a narrower job, is the only thing that moves a draft onto the published path, and when it does, it stamps a record of what it moved, computed from the exact bytes that landed. The thing certifying the work is a different actor than the thing that produced it, which is the same independence the verifier essay argues for, carried from grading into permissions. Be exact about the scope, though. This constrains the worker, not every actor. A different principal that does have a shell, running the same copy command from earlier, can still reach the live path directly. What the boundary removes is the writer's ability to wave its own work through, and it does not seal the path against everyone.

Even that is not a wall, and the honest move is to say so out loud. The stamp the promotion step writes is a plain file. Anyone able to write files could hand-author a fake one that looks exactly like the real thing, and nothing behind it proves otherwise. So the record is not proof the work was done. It is a convention that makes faking it a deliberate, visible act instead of an easy accident. That is a real improvement and a modest one, and the whole value depends on saying which of the two it is. So the stamp gets called a convention, never tamper-proof, because a reader told it cannot be forged will trust a forged one the day it shows up.

This is why publishing the limits of your own controls tends to earn trust instead of spending it. I keep a plain document for each of these gates that lists, in order, what it genuinely prevents, what it only makes louder, and the exact ways it can be walked around. The document reads like a list of weaknesses, and every instinct says to keep it private, so writing it down and leaving it where people can find it is the part that takes some deliberate effort.

The alternative is worse. Once I wrote a note about one of my own checks that said it passed a particular bad paragraph clean. That was true of the version of the check that existed when I wrote it. A later version of the same check caught part of what I had claimed it missed, which meant my note was now overstating the hole. The honest fix was to go back and correct the claim in place, so the document described the tool I actually had instead of one that no longer existed. Overstating a hole causes its own trouble, because a reader planning around a weakness that is no longer there is planning around a tool that is not the one on disk.

What a gate can prove is narrow. It proves a step ran and left a mark; it cannot prove the mark was earned, and whether the page is any good is a separate question the chain essay already takes up. Kept honest about its shape, a gate catches the ordinary failures cheaply, makes the deliberate ones visible, and puts the placing of a file in steadier hands than the writing of it. That is the honest description of what these controls buy, and it is less than the word enforcement usually implies.

So none of these gates get turned off. The thing that changed is what gets shipped alongside them, a short plain note on each one saying what it stops, what it only makes noisier, and the specific ways around it. The gate does the cheap work it is good at, and the note keeps anyone from asking it to do work it cannot. That pairing, the control plus the honest account of its holes, is the part I would not skip.
